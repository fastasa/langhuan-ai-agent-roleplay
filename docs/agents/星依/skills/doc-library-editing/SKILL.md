# 星依文档库编辑手册

> 运行时 Skill：`xingyi.doc-library-editing`。凡要修改文档库，先调用 `readDocLibraryEditingSkill` 读取本手册；这里是操作正文唯一真值，TypeScript 不保留镜像规则。

## 一、层级与权限边界

- 文档库是本机工作区级的全局资料树，高于世界和会话。星依读写 `domain=docLibrary` 时不需要当前会话，也不需要先把会话挂到某个世界。
- 世界只保存“这个世界关联哪些文档”的链接；会话挂载世界只决定聊天召回与剧情上下文投影，不授予也不撤销文档库编辑权限。
- 用户点名某个世界、树簇或资料分支时，先用 `listUnitTree` 在全局树中按标题、路径或 unitId 寻址；不要要求用户切换会话、创建会话或挂载世界。
- `characterBrain` 是角色私有大脑，不是文档库。只有用户明确说要改某个角色的大脑时，才把 `domain` 改成 `characterBrain` 并提供 `characterName`。

## 二、文档库的每一层是什么、从哪里来

1. **世界树根**：运行时为了浏览整库生成的虚拟根，只负责承载根级树簇，不是正文文件，也不直接写入。
2. **树簇**：根下的一级文件夹，常用来承载一个世界、一套项目资料或一套互相关联的知识。它在字段树中是稳定 folder 节点。
3. **枝**：树簇下的任意文件夹/分组，可继续包含枝和文档。枝的结构真值同样是 folder 节点，移动和改名操作应保持它的稳定身份。
4. **概览正文**：每个树簇和枝必须有一份 `index.md`。运行时会把这份文档折叠到枝本身，用户点击枝时右侧显示的正是它；它不应再作为普通叶文档重复出现。
5. **桠/文档**：承载实际 Markdown 正文的叶单位，正式身份是 documentId；可读路径只用于定位和展示，不是稳定身份。
6. **编译页**：附着在概览或叶文档上的召回元数据，包含摘要、标签、类型、关系提示以及可选评分。正文回答“资料写了什么”，编译页回答“怎样被召回、分类和连到别的单位”。
7. **关系提示**：编译页中的关系语句，通常写成 `[[源单位]]_谓词_[[目标单位]]`；它会投影到关系视图和扩展召回。没有正文证据时不要编造关系。
8. **字段树与可读路径**：`treeNodes/treeOrders` 是现役结构真值；`displayPath/manualTreeOrders` 只作可读路径与兼容派生。星依只调用单位工具，绝不手写或整包替换这些底层字段。

## 三、可做的事情与正式工具

- 看结构：`listUnitTree(domain='docLibrary')`；范围大时用 `parent` 只看一棵子树。
- 读正文：`readUnit`。读枝会同时返回它的概览正文和直属子单位；读叶文档返回正文与已有编译页摘要。
- 新建：`createUnit`。`kind='folder'` 创建枝，`body` 是其概览正文；`kind='document'` 创建叶文档并必须给 `parent`。
- 改正文：先 `readUnit` 读取最新内容，再用 `editUnitBody` 做唯一锚点替换；只有确实要重写整篇时才整段覆盖。
- 改编译页：用 `editUnitCompilePage` 定点改摘要或覆盖标签、类型、关系提示；它不要求文档库页面打开。
- 改名、移动、删除：分别用 `renameUnit`、`moveUnit`、`deleteUnit`。先读树确认准确 unitId；删除不可恢复，必须把子孙范围和关系影响看清后再走确认卡。
- 体检：用 `diagnoseCompilePages` 查看黄灯字段缺失和红灯关系错误；可用 `parent` 限定受影响子树。
- `generateCompilePage` 是整页 AI 生成入口，依赖对应页面在场；星依浮坞跨页面工作时，优先依据正文直接调用页面无关的 `editUnitCompilePage`。

## 四、新建枝的硬规则

1. 禁止创建没有概览正文的空枝。`createUnit(kind='folder')` 会把 folder 与 `index.md` 在同一次保存里创建；用户给了概览就原样采用，没有给时工具只会写结构性默认概览。
2. 遇到历史遗留的空枝，不要要求用户重新建枝，也不要绕过单位工具手写底层字段；直接用 `editUnitBody` 的 `body` 提供完整概览，工具会补建 `index.md` 并绑定为该枝的概览文档。空枝没有旧正文，不能使用锚点替换。
3. 如果用户给的信息足够，`body` 应写成简洁、真实的枝概览：说明本枝收什么、当前覆盖哪些主题、重要边界是什么；不要只写标题，也不要发明世界事实。
4. 用不存在的 `/完整/路径` 新建文档时，沿途自动创建的每一级枝也会带 `index.md`。操作完成后仍要检查这些概览是否需要按用户资料补充。
5. 创建后再 `readUnit` 复读目标枝，确认概览正文可见、直属子单位正确；不要把“命令成功”直接当成阅读态验收。

## 五、正文变更与编译页同步

每次新增、编辑、改名、移动或删除文档库内容，都要做一次“编译影响判断”，不能只改正文就结束：

1. **新增文档或枝概览**：读正文后补摘要、标签、类型和有证据的关系提示；使用 `editUnitCompilePage` 写正式编译页。
2. **编辑正文**：若对象定义、关键事实、名称、关系或范围发生变化，同轮更新编译页；纯错字、标点或不影响语义的排版修改可以不改，但要明确判断过。
3. **改名**：检查该单位自身摘要/标签，以及其它单位关系提示里是否仍引用旧名；有旧引用就逐项改正。
4. **移动**：路径变化本身不等于事实变化；但如果移动表达了新的归属或分类，就同步更新摘要、标签或关系。
5. **删除**：删除前检查是否有其它关系提示指向它；删除后修掉失效关系，不能留下“目标不存在”红灯。
6. 完成一组改动后，对受影响子树调用 `diagnoseCompilePages`。继续修到相关红灯消失、该补的黄灯补齐；只剩没有事实依据或需要用户决定的项时，明确列出原因，不得硬编到“全绿”。

## 六、可靠操作顺序

1. `listUnitTree` 定位目标和父级；同名时改用 unitId。
2. `readUnit` 读取目标正文；涉及关系时同时读相关单位。
3. 判断本轮改动会影响哪些正文、概览、编译页和关系提示。
4. 发起相应写工具并等待确认卡；用户取消就停止该项，不换说法绕过确认。
5. 写后重新 `readUnit/listUnitTree` 复核结构与正文。
6. 更新必要的编译页，再 `diagnoseCompilePages(parent=受影响子树)` 复诊。
7. 汇报正文改了什么、概览是否存在、编译页处理结果、还有哪些需用户拍板。

## 七、常见错误与下一步

- “枝没有概览文档”：这是存量缺口。若用户授权修复，在该枝内补 `index.md` 概览后再编辑；不要继续把正文写到不存在的枝体上。
- “没有找到/匹配多个单位”：重新 `listUnitTree`，使用准确 unitId；不要凭相似标题猜。
- “页面未打开”：只有整页生成类入口需要页面。读取、单位 CRUD、`editUnitCompilePage` 和 `diagnoseCompilePages` 都应继续走页面无关链路。
- “确认期间目标已变化”：重新读最新树和正文，再按新真值规划；不要复用旧确认卡参数。
- 字段树护栏拒绝：本次未保存。把回执原样告诉用户，先排除结构冲突，不得绕过正式保存入口直接写路径字段。
