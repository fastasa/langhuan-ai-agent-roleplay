# 星依任务路由与知识补全

## 一、任务路由

### 0.1 先拆四个槽位：资料源、操作对象、动作、写入目标
一句话里出现多个功能名时，不要看到第一个名词就把整项任务锁进那个功能。动工具前先在心里拆清四件事：

1. **资料源**：事实从哪里读取，例如文档库、某段对话、角色大脑或地图。
2. **操作对象**：真正要创建、修改、移动或删除的东西，例如正式角色、角色分组、文档单位、状态栏。
3. **动作**：查、生成、修改、移动、归类、删除或总结。
4. **写入目标**：结果最后落到哪份正式真值，例如角色列表、角色页分组、文档库树或某个会话。

资料源和写入目标可以不同。例：“把文档库的咒术回战里还没生成的角色生成出来，再放进角色页的咒术回战组”：

- 资料源 = 文档库“咒术回战”人物资料。
- 操作对象 = 正式角色 + 角色页分组。
- 动作 = 对比缺失、批量生成、归组。
- 写入目标 = 正式角色列表与角色 `groupId/group_id`，不是文档库树。

### 0.2 跨领域任务按依赖顺序连续推进
同一句话横跨多个功能区时，按真实依赖串起工具，不要强行选一个领域，也不要每做一步就停：

1. 从资料源读取并整理候选事实。
2. 从写入目标读取当前真值，做差集或冲突检查。
3. 必要时先创建目标容器（例如角色分组）。
4. 执行创建或修改；多个独立对象优先使用批量/并行工具。
5. 把已有对象和新对象统一归到目标。
6. 再读一次目标真值验收，最后汇报成功、跳过、部分成功和失败。

只有某个关键槽位确实存在多个会改变结果的解释，且工具/现状无法消歧时，才用 askUser。用户已经明确说“角色页”“正式角色”“联系人角色分组”时，不得再拿文档库枝结构反问。

### 0.3 同名词先看对象，不凭“分组”二字选工具
“分组、角色、移动、生成”在琅嬛里可能属于不同领域，必须看它修饰的对象：

- **角色页分组 / 联系人分组 / 正式角色归类**：使用 listCharacterGroups、createCharacterGroup、renameCharacterGroup、assignCharactersToGroup、deleteCharacterGroup、moveCharacterGroup。
- **文档库枝、文件夹、单位分组**：使用 listUnitTree、createUnit、moveUnit 等文档单位工具。
- **角色大脑里的灵魂组/轨迹组**：使用 domain=characterBrain 的单位工具。
- **文档库里类型为 character 的单位**只是角色资料文档，不等于角色页已经存在同名正式角色。

moveUnit 永远只移动文档库或角色大脑的树单位，不能改变正式角色的角色页分组。assignCharactersToGroup 才改变正式角色的 `groupId/group_id`。

## 二、知识不足时去哪里补

### 0.4 知识不足时去哪里补：先判断缺的是哪一种知识
不要把所有“不知道”都交给一次模糊搜索，也不要直接问用户。先分类：

1. **连知识库里有哪些主题或准确术语都不知道**：先用 listXingyiKnowledgeTopics 浏览目录；可带宽泛 query 缩小范围。
2. **不知道任务该走哪个功能或工具**：查 searchXingyiKnowledge，关键词写“对象 + 动作 + 来源/目标”，例如“文档库资料 正式角色 角色分组 归类”；它只返回候选摘要，选定后必须用 readXingyiKnowledgeTopic 按准确 topicId 精读完整规则。
3. **不知道当前系统有什么 / 现在有哪些对象**：调用对应业务 list/read 工具现查。角色与分组用 listCharacterGroups；文档树用 listUnitTree；会话用 listChatContacts；世界用 listWorlds；状态栏用 listStatusSystem。
4. **不知道对象的事实内容**：回到资料源检索和精读。文档库用 searchWorldText/recallSemantic + fetchUnitDetail/readUnit；正式角色用 readCharacterBrain；对话事实用 readChatProjection/searchChatProjection。
5. **不知道某能力此刻是否可用或参数怎么填**：以当轮工具目录与工具 schema 为准。知识库只讲工作流，不得凭旧文字虚构不存在的工具。
6. **资料渠道已经查完仍缺关键事实**：可派采风就 dispatchResearch；仍不足才 askUser，并写明查过什么、缺什么、最接近的候选是什么。

### 0.5 知识来源的优先级与冲突处理
稳定边界看常驻纲领与按需知识；当前名称、ID、成员和状态看工具现查结果；具体世界或角色事实看用户自己的文档、对话和角色大脑。发生冲突时：

- 当轮工具 schema 比知识库里的旧工具名更可信。
- list/read 返回的当前状态比知识库举例更可信。
- 用户明确指定的对象和目标比默认路由更优先。
- 知识库与工具明显不一致时，不要猜成功；按工具真值执行或如实报告知识已过期。
